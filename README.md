# SANGA RWANDA — MVP prototype

Responsive website with SQLite-backed search, merchant registration/login, merchant listings, admin statistics, and **simulated** premium requests.

## Run locally

```bash
python -m venv .venv
source .venv/bin/activate # Windows: .venv\Scripts\activate
pip install -r requirements.txt
export SECRET_KEY='replace-with-a-random-long-secret'
export ADMIN_EMAIL='admin@example.com'
export ADMIN_PASSWORD='choose-a-strong-password'
python app.py
```

Visit http://127.0.0.1:5000. For a quick demo only: merchant@demo.sanga / DemoOnly123!. **Remove demo account and example listings before launch.** The admin account is created only if environment variables are supplied on first initialization.

## What works
- Search by title, description, city, country, category, maximum price
- Merchant registration, password hashing, session login, CSRF checks
- Merchant dashboard with add/delete listings
- Admin dashboard: number of users, shops, listings, payment records and **confirmed** revenue
- SQLite persistence, read-only JSON endpoint `/api/listings`
- Premium requests recorded as `pending` with **no charge**

## Not yet production ready
- No live payment gateway or API credentials; no real Google/LinkedIn/TikTok integrations
- No email verification, password reset, rate limits, audit logs, media uploads, vendor verification, or full legal/privacy documentation
- SQLite and local sessions are suitable for local testing; production should use PostgreSQL, durable session/secret management, backups, TLS/HTTPS, monitoring and secure deployment
- Set up migration scripts, staff approval workflow and content moderation before public use
- Protect user information, comply with applicable laws, and ensure lawful merchant verification

## Integration plan
1. **Google Places API (New):** use a backend proxy with restricted API key, text search and place details; comply with Google's display attribution, caching, and terms. Do not bulk-copy Google's place database.
2. **LinkedIn:** developer app + OAuth and approved scopes; not a general-purpose source of profiles/company data without permission.
3. **WhatsApp Business Platform:** official business messaging onboarding and opt-in, server webhooks; no automatic messaging without required permission.
4. **TikTok:** embed publicly embeddable videos where allowed or approved developer APIs; do not scrape private content.
5. **Payments:** integrate a licensed local payment service with merchant onboarding, secure server callbacks/webhooks and payment reconciliation. Only mark paid after verified provider confirmation.
6. Add explicit source attribution, merchant-owned records, update dates, consent, privacy and removal workflows.

Suggested next iteration: PostgreSQL + production auth, listings moderation, payments sandbox, merchant photos, and approved API connector.


## Deploy a PRIVATE TEST on Render (not production)

1. Create a **private** GitHub repository named `sanga-rwanda-demo`. Do not upload passwords or `.env` files.
2. Upload the project files including `render.yaml`, `app.py`, `requirements.txt`, `templates/`, `static/`.
3. In Render, select **New > Blueprint**, connect the repository, and approve the `render.yaml` blueprint. Check the free plan is available before approval.
4. Wait for the deploy to finish. Render will show the real `*.onrender.com` URL. Do not guess the URL.
5. Test search and the sample merchant login (`merchant@demo.sanga` / `DemoOnly123!`) **with dummy data only**.

**SECURITY AND DATA WARNING:** This deployment is for temporary demonstration ONLY. It uses an ephemeral SQLite file: data can disappear after restart or redeploy. The demo merchant login is public knowledge, and anyone can register; do not enter personal information, real merchant data, financial details or accept real payments. No admin account is provisioned by this blueprint. Do not publicize the URL. Before any public launch, remove the demo login and seed data, switch to persistent PostgreSQL, add email verification, rate limits, abuse controls, privacy policies, backups, and payment verification. The `SECRET_KEY` is generated by Render and should never be shared.
